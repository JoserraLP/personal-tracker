# ADR-053: granting `workflows: write` to the auto-resolve-issues workflow (issue #141)

## Status
Accepted

## Date
2026-08-08

## Context

The workflow `.github/workflows/auto-resolve-issues.yml` (ADR-047) launches
headless OpenCode sessions that resolve issues automatically: the agent
edits code, commits, pushes branches and creates PRs against `dev` using
the `GITHUB_TOKEN` generated by GitHub Actions. That token's permissions
are declared explicitly in the workflow's own `permissions:` block.

When resolving issue #124 (which modified `.github/workflows/issues-done-on-dev.yml`),
the agent's session edited the workflow and created the local commit, but
the `git push` was **rejected by GitHub**: repositories are configured to
reject any push that modifies `.github/workflows/*.yml` files if the
token used lacks the `workflows` scope (typical error «refusing to allow a
GitHub App or bot to create or update workflow ... without `workflows`
permission»). The run hung for ~56 minutes until the timeout and failed
(run 31248694436 of 2026-08-08).

The `workflows` scope is special: **it cannot be granted from the
repository's Settings UI** (the "Workflow permissions" setting only
controls the default scopes, not `workflows`). It is only granted by
declaring it in the workflow's YAML (or with a user PAT with that scope,
rejected because it requires manual secret rotation).

Related issue: #141 — https://github.com/gonzalitojh/Registro-personal/issues/141

## Decision

Add `workflows: write` to the `permissions:` block of
`.github/workflows/auto-resolve-issues.yml`, alongside the existing scopes:

```yaml
permissions:
  contents: write      # commits/push del agente (flujo SDD: rama + PR)
  pull-requests: write # creación de la PR por el publisher
  issues: write        # labels (set-state) y comentarios
  actions: write       # lanzar workflow_dispatch de deploy-all-branches tras sesión exitosa
  workflows: write     # el agente puede modificar .github/workflows/*.yml (issue #141)
```

No other aspect of the workflow is touched: triggers, `concurrency`,
jobs, steps and comments remain identical.

## Considerations

- **The `GITHUB_TOKEN`'s pushes do not trigger new workflow runs**: a
  commit/push made with the session's token does not reactivate
  `auto-resolve-issues` (GitHub's anti-loop protection), so modifying
  workflows from the agent generates no recursion.
- **Activation via the default branch**: the `issues` and `issue_comment`
  events use the `main` workflow version; the fix fully activates
  after the `dev` → `main` promotion (mechanics already documented in
  ADR-047/issue #120). With `workflow_dispatch` it can be validated
  beforehand from the branch itself.
- **Minimum privilege escalation**: `workflows: write` allows modifying
  `.github/workflows/*.yml` files. It is acceptable because the token
  already had `contents: write` (it could modify any other repo file), it
  is ephemeral and per-run, and the agent's prompt includes
  anti-exfiltration instructions for `GH_TOKEN`/`OPENCODE_API_KEY` and
  protection against prompt injection from the issues' contents.
- **No visible changes for the user**: AGENTS.md's rule 3 does not apply
  (`docs/manual-de-usuario.md` not touched).

## Rejected alternatives

- **User PAT with the `workflows` scope**: rejected — it would require
  creating a secret, manual rotation, and it distorts the CI design with
  a bot identity.
- **Doing nothing / granting via UI**: not possible in Settings; the UI
  does not expose the `workflows` scope. Declaring it in the YAML is
  necessary.
- **Separate job with its own token for workflow files**: rejected — more
  complex and the agent would need the scope during the whole SDD flow,
  not just one job.

## Consequences

### Positive

- **The agent can push changes to `.github/workflows/*.yml`**: the
  «refusing to allow ... without `workflows` permission» error and failed
  runs like #124's resolution are avoided.
- **Unblocks future infrastructure issues**: any `ai` issue that
  requires modifying workflows can complete in a single session.
- **`wip-save` (issue #128) also benefits**: WIP progress pushes
  including workflow changes are no longer rejected.

### Negative / Risks

- **Greater bot token capability**: a token with `workflows: write` can
  rewrite the workflow itself. Mitigated with the bot identity,
  the hardened prompt, the anti-injection of issue bodies and the existing
  single-flight `concurrency`.
- **Delayed activation**: until the dev → main promotion, the automatic
  events keep using the version without the scope (current behavior).

### Neutral

- **`docs/manual-de-usuario.md` unchanged**: internal CI infrastructure,
  not visible to the end user (rule 3 does not apply).
- **Other workflows intact**: `issues-done-on-dev.yml` and
  `deploy-all-branches.yml` do not require the scope (it is
  `auto-resolve-issues.yml`'s agents who push workflow changes).
